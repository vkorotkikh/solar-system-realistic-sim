1. Executive verdict

What actually ships. index.html → src/main.ts builds a "Sun Model Lab" (its own eyebrow text: "Sun-Focus Branch" — even though this is main; commit d1484e8 2026-02-23 "Revise index.html for Sun Model Lab transition" landed on main). It renders: a procedurally-shaded Sun fed by the backend's procedural corona model (when the backend is up), the 8 planets + Pluto on fixed J2000 mean elements propagated in a worker, a 15,000-asteroid instanced mesh, a 5,000-body synthetic Kuiper belt, orbit lines, labels, a body explorer, and a "Cataclysmic Events" panel that fires a speculative SMBH shockwave / "H29 metric-frame-dragging slipstream" effect. 30 of 62 TypeScript files are reachable; the other 32 (satellites, planet textures, nearby star systems, Milky Way, LOD, trajectory UI, WebSocket engine client, planner) are dormant. 424 moons are bundled and propagated but hard-disabled (const showMoons = false, src/main.ts:380).

Headline findings (all high-confidence, re-executed):

  1. The asteroid belt is not where the user thinks it is. The GPU shader adds the orbital position before the per-instance matrix (random rotation × body-radius scale), so all 15,000 asteroids collapse into a ~0.01 AU sphere hidden inside the Sun's display radius (beltRenderer.ts:176-184 vs :396-413). A/B render with the order swapped produces the belt (§7.5, screenshots $SP/out/ME/browser/beltbig_*.png).
  2. The default backend N-body path does not work with the REBOUND version an unpinned rebound>=4.0.0 resolves to today (5.1.1): 'Simulation' object has no attribute 'ri_ias15' → WebSocket closes 1011. /health nonetheless reports rebound: available, fidelity: high. The only test touching that path mocks the missing attribute (test_seek_optimizations.py:37). whfast/mercurius work.
  3. The committed "strict GMAT/Orekit/Tudat" benchmark references are not reproducible and the model is right. An independent universal-variable Lambert on JPL Horizons state vectors reproduces the model's Δv sums to ≤15 m/s for all three windows (7.640 / 39.989 / 51.634 km/s vs model 7.637 / 39.983 / 51.620), while the committed references (8.490 / 7.108 / 16.873) cannot be produced by any 0-rev Lambert solution between the stated dates. Git history shows the references began as round placeholders (8.6 / 7.2 / 17.0, tolerances 5–10 km/s, source "…-blend") and were replaced one day later by 5-decimal "tool captures" sharing a single identical timestamp. passRate 0.0 is an oracle failure, not a solver failure.
  4. The "high-fidelity" N-body engine is less accurate than the browser's Kepler fallback because it injects JPL mean elements into an integrator as if they were osculating: Saturn is 60,200,000 km (≈2.5°) off Horizons on 2026-08-23 vs 1,180,000 km for the Kepler path; Earth 232,000 km vs 10,500 km. Isolation runs show Sun+Saturn alone reproduces the Kepler error; adding Jupiter produces the 60 M km (§7.2).
  5. Moon positions in non-ecliptic source frames are wrong at their own epoch: the Laplace/equatorial→ecliptic conversion rotates only the orbit normal and never re-references ω/M (catalog.ts:193-210), so Io is 828,000 km (1.97 orbital radii) from its Horizons position at J2000 with a 34 km/s velocity error; Callisto 1.86 radii, Triton 1.76, Enceladus 1.9. (Hidden from users today; propagated anyway.)
  6. Lambert solutions are served without a time-of-flight certificate. For infeasible TOFs the solver returns its best-sampled z with residuals of days (1-day Earth→Mars request → a 4.96-day orbit) as HTTP 200; endpoint miss distances up to 2.8×10⁸ km. Well-posed cases agree with pykep (Izzo) to ≤1.3×10⁻⁵ km/s.
