

# AREA: backend-route (/solar/physics lifecycle, sample_state stage map, caches, provenance, H-2 exposure)

## Summary
The Sun-physics request is slow for one main reason: every request redraws about 120 magnetic field lines and a solar-wind map from scratch. That takes about 4-6 seconds of CPU and is more than 99% of the work; everything else takes about 20 milliseconds. None of it is reused, because the cache matches on the exact simulation time down to a fraction of a millisecond. With live data turned on, even the same time on a paused simulation gets a fresh result, because the answer drifts with the real clock. Every request with a new time also makes 13 calls to outside services. One of them is a 2.9 MB sunspot file that only changes once a month. One of the services (NOAA) returns 404, and the magnetogram download (GONG) never works, because the code expects files where the archive now lists only folders. So the 'magnetogram-driven' field lines are always made up from a synthetic map. When the browser gives up at 2.6 s, the server keeps working: I showed in-process that the two work slots stay taken until the job finishes, not when it times out. The same two worker threads also serve route planning, so abandoned Sun jobs block that feature too. Running two Sun jobs at once made each one about 3x slower instead of doubling throughput. Unblocking H-1 as-is causes two new problems. The field lines and spiral arms the UI would start drawing come from the known-wrong solver (H-2). And a healthy 0.9 s poll rate is almost twice the server's limit of 36 requests per minute, so the client would get 429 errors within about 30 s. The fix that fits the code: cache only the expensive field-line step, using a coarse time bucket (about 14.4 sim-minutes already matches how the synthetic map changes). Compute the cheap parts on each request, never run the expensive step while a user waits, and label the response honestly (synthetic vs observed, stale, validated or not).

## Facts
1. [fact/high] Request lifecycle, part 1: the /solar/physics route is async and runs on the event loop. ## hidden_problems
- Making requests fast without other changes turns the app into a traffic generator for third-party services. Each new sim jd triggers about 13 outbound calls (SWPC, SILSO 2.9 MB, 10 Helioviewer, GONG listing), because the snapshot is keyed on the exact sim jd (solar_realtime_data.py:131) and PFSS always retries GONG (pfss_magnetogram.py:1253).
- Rate limit vs poll: the client polls every 900 ms after success (about 66/min), but the server allows 36 per 60 s per IP (server.py:168-177). Once H-1 is fixed, the client gets 429 after about 30 s and falls into the 6 s error backoff. All local tabs share one identity (127.0.0.1).
- Raising the client timeout alone does not help. Concurrency=2 makes each job about 3x slower through GIL contention. Both slots stay held by abandoned work (the slot is freed at worker completion; the 12 s server timeout frees nothing). The server budget (12 s) is also far above the client's (2.6 s).
- A cache hit still goes through the 2-slot guard and the shared executor. Unless hits are served before admission, cached answers will still get 503 while orphaned jobs hold both slots.
- The PFSS cache key includes the exact activity float. Under hybrid+live, activity drifts every second through datetime.now() freshness weights (solar_physics.py:391-395), so quantizing jd alone will NOT produce cache hits. The activity (or the observed confidence) must be quantized or frozen per bucket too.
- The synthetic magnetogram and the equatorial coronal holes re-randomize every 0.01 sim-day (int(jd*100) % 99991). At typical sim rates (days per second), every poll lands in a new bucket, so a jd-bucketed cache has near-zero hit rate unless PFSS is decoupled from jd (e.g., seeded per Carrington rotation) or precomputed ahead of time.
- Fixing GONG exposes more bugs. The decomposition assumes a uniform-colatitude grid with row 0 at the north pole (pfss_magnetogram.py:337), but GONG bqs maps are sine-latitude (docstring :134), and FITS row order is probably south to north (inference). The 'any mrbqs file' fallback can pick the wrong rotation (:169-177), and the read is unbounded.
- Any exception other than a timeout becomes a 500 without CORS headers (measured). The browser then shows it as a CORS failure, which will look like the preview-origin CORS bug and confuse debugging.
- Unblocking H-1 immediately renders the H-2-wrong PFSS lines (solarMagnetics.ts:303-304). It also renders Parker spiral arms whose winding comes from WSA speeds computed on the wrong field (sunVisuals.ts:1485-1486), because has_wsa is always true.
- Provenance is partly false. gong_synoptic.ok is always true (a stub), live_data_enabled=true is set even under synthetic, a failed live fetch looks the same as 'not requested', and 'hybrid' still blends present-day SILSO data into any historical epoch.
- The AIA tile route ignores the image_id the frontend sends and calls latest(jd=None). On a cold cache that is a full ~3.6 s snapshot fetch inside a 4.0 s budget on its own 2-slot executor, so it will often 503. It also serves the current image even when the physics response referred to an older one.
- Cached PFSS dicts are shared by reference with live responses (shallow copy at solar_physics.py:1124). Any future per-request post-processing done in place (rounding, trimming) would corrupt the cache.
- About 0.63-0.78 MB of JSON per response, encoded on the event loop (~43 ms), with no gzip. At 0.9 s polling that is about 0.7 MB/s per client, and it blocks the loop as more clients join.
- Caches, guards and rate-limit dictionaries are per process. Running uvicorn with --workers N multiplies upstream fan-out and the concurrency limits, and repeats the precompute in every process. The rate-limit dictionary also never evicts identities (server.py:283, :354) and trusts X-Forwarded-For.
## fix_implications
- Split the work. Compute the cheap part on every request at the exact jd (activity, features, coronal holes, spiral geometry: about 20 ms total). Compute the PFSS+WSA field (99.6% of CPU) only through a cache or precompute layer, never on the request path while a user waits.
- PFSS cache key: (solver_version, magnetogram_source_id ['synthetic-v1' or the GONG filename], seed bucket [today int(jd*100) % 99991, i.e. 0.01 d; or the Carrington rotation if the synthetic generator is re-seeded per CR], activity quantized to about 0.01 (about 1 bucket per sim-day), n_lines, lmax). Remove gong_timeout_s from the key. Exclude max_features: it does not affect PFSS.
- Bucket size: 0.01 d is safe for today's output. Within a bucket PFSS changes by at most 0.05 R_sun with 0 topology flips, so snapping loses nothing visible. Coarser buckets need a model change (per-CR seeding plus differential rotation) and an owner decision.
- TTL: synthetic PFSS is a pure function of its key, so it needs no TTL (evict by LRU or memory). GONG-based entries: TTL about 1 day, keyed by filename. Realtime snapshot: key 'latest' sources (SWPC, SILSO) by a wall-clock bucket (SWPC 1-5 min, SILSO 12-24 h) and key AIA by the closest-image time bucket (5-10 min), never by the exact sim jd.
- Invalidate on a solver or model version string in the key and in the response (e.g., 'quasi_mhd_corona_v4' plus a pfss_solver version). The H-2 fix must bump it so wrong cached lines are dropped.
- Memory: about 1.23 MB Python heap per PFSS entry (about 0.21 MB JSON + 0.11 MB WSA arrays). 100 entries in object form is about 125 MB. Storing pre-serialized (and gzipped) bytes plus the WSA arrays is about 0.2-0.3 MB per entry. The current max_entries=3 cannot cover a moving sim clock anyway.
- Serve cache hits (and stale-while-revalidate results) BEFORE the concurrency guard and without the heavy executor. Keep the guard and executor only for cache-fill jobs. Consider one dedicated background worker so solar work cannot starve porkchop and mission plans.
- Precompute or stale-serve strategy: when the bucket changes, return the last good PFSS with a staleness field and fill in the background with single-flight plus follower timeouts. Optionally compute ahead along the sim timeline. Because of the GIL, parallel threads do not add throughput; use one worker or a process pool.
- Make the compute cheaper where it counts. trace_field_lines evaluates the field one point at a time in scalar Python (pfss_magnetogram.py:677, :697-706) although a batch evaluator exists (:532-603). The WSA theta_b and lookup loops are also pure Python (:997-1021, :1071-1087).
- Align the client poll interval with the rate limit (36 per 60 s means at least 1.7 s between requests), or exempt cache hits. Add Retry-After and machine-readable error codes to the timeout 503. Add an exception handler so a 500 carries CORS headers and a JSON body.

# AREA: realtime-upstream

## Summary
Of the four outside data sources the "live Sun" feature depends on, only one fully works, and the part that does work shows the wrong picture. NOAA retired the solar-wind feed the code uses on or about 30 April 2026, so every request since then has returned "not found" and solar-wind data has been missing for about five months with no one noticing. The magnetic-map download from the GONG observatory never succeeds, because it looks in a folder layout that doesn't exist, so the magnetic field lines are always computer-generated even though the status report says the source is healthy. The sunspot file from SILSO does work, but the code downloads the whole 2.9 MB file on almost every sun update, and that file only changes about once a month. The SDO images from Helioviewer do arrive, but each one is a close-up covering about 3% of the Sun's disk, and it gets stretched around the whole globe. Fixing H-1 alone would therefore start showing users a wrong-looking Sun. It would also mean each open browser tab triggers roughly 8 to 13 requests to outside services every few seconds, about 3 GB an hour of repeated sunspot downloads per tab. That breaks NOAA's published guidance on automated access, and we display none of the credits the data providers ask for. All of these sources change slowly: every minute for solar wind, every 11 to 16 minutes for the SDO images we can get, hourly for magnetic maps, monthly for sunspots. A background job on the server that fetches each source on its own schedule and answers users from memory is a very good fit, and it would cut outside traffic to about 200 requests an hour no matter how many people are using the app. Moving the fetching off the request path removes 1.8 to 3.1 s from each sun update, but the physics calculation itself still took 7.8 s in my run, so this alone will not make updates fit the browser's 2.6 s limit. The SILSO sunspot data is licensed for non-commercial use only, which matters if the app is ever offered commercially.

## hidden_problems
- Making /solar/physics succeed (H-1) would immediately start mapping a 3%-of-disk native-resolution AIA crop around the whole Sun as an equirectangular texture. Switching to a full-disk image without changing the shader would wrap black sky plus a disk around the sphere instead.
- The SWPC feeds have 404'd since about 2026-04-30. Re-pointing to json/rtsw/* is not a URL swap: the schema changed (list of objects, numeric values, renamed fields), rows are newest-first (the old parser's reversed() would pick the OLDEST row), and several spacecraft are interleaved. The newest row is typically an INACTIVE spacecraft with very different values (density 0.17 vs 6.85 /cc). The active mag feed can lag about 1.6 h behind the inactive one.
- A snapshot where every source failed is cached as a success for the full TTL (120 s), so short upstream blips become 2-minute outages. The tile route then returns 503 even after the upstream recovers.
- There is no stale-while-error: an outage right after TTL expiry discards the last good data.
- The snapshot and PFSS caches are keyed by the exact jd, and a unit test (test_snapshot_cache_isolated_by_requested_julian_date) enforces this. Any quantisation or jd-independent refresher must change that test deliberately, not 'fix' it.
- The 3.8 s timeout is per socket operation. A slow-drip upstream holds a worker indefinitely, so per-request deadlines need an overall wall-clock cap (e.g. httpx timeout plus asyncio deadline).
- Single-flight followers raise TimeoutError after 4.3 s. In the sync /solar/realtime route this surfaces as HTTP 500. In the tile route, Python 3.11+ makes builtin TimeoutError == asyncio.TimeoutError, so it is reported as 'AIA tile generation timed out'.
- One getClosestImage failure (unguarded call at solar_realtime_data.py:706) aborts all 5 AIA channels, and the plasma failure prevents the mag fetch. Per-feed isolation is missing.
- GONG ingestion is silently dead (wrong directory level), and source_status claims gong_synoptic ok:true. Fixing it will change PFSS output from synthetic to observed, which interacts with H-2 (the Legendre recurrence bug): the first real magnetograms would be solved with the wrong recurrence.
- The coronal-hole detector hard-codes r_sun = 0.90 x half-width. With a full-disk 512 px image (rsun about 199 px, i.e. 0.78 x half-width) it would still misplace the disk. It must use rsun/scale from the Helioviewer metadata.
- The tile route ignores image_id/v and always serves 'latest'. The frontend's imageId comes from the jd-specific snapshot and is recorded as loaded even if a different image was served.
- Frontend freshness uses Date.parse on a zone-less 'YYYY-MM-DD HH:MM:SS' string, so it is time-zone dependent. The backend should emit ISO-8601 with Z.
- 'Live' data is blended into simulated dates months in the future: the default 4 sim-days per second, Helioviewer 'closest' for future dates returns the latest image, and SWPC and SILSO are always 'latest'.
- Per-process caches: running uvicorn with --workers N (or several replicas) multiplies upstream polling and cache misses by N unless the refresher is shared or leader-elected.
- The rate-limit identity trusts the first X-Forwarded-For hop (server.py:323-330), and /solar/realtime has no rate limit at all while force_refresh bypasses cache and backoff. Once upstreams are fixed, this is an easy way to make the server hammer NOAA, SILSO and Helioviewer.
- SILSO data is CC BY-NC 4.0 (non-commercial). There is no UI attribution for SILSO, NASA/SDO or GONG today.
- The Helioviewer-derived 'activity proxy' and the backend preferred_channel (argmax across channels) are computed on the crop and on colour-mapped PNG luma. They are not physically meaningful, and the selected channel flips arbitrarily (aia_304 was chosen here).
## fix_implications
- Decouple the request path from upstream I/O entirely. Have one background refresher per process (its own thread or asyncio task, not the anyio pool and not _heavy_compute_executor) that fetches each source on its own schedule, keeps per-source last-good values with fetched_at, age and status, and lets /solar/physics and /solar/realtime read from memory with zero network calls.
- Recommended refresh periods: SWPC RTSW every 60 s (min) to 300 s, with Accept-Encoding gzip (94 KB vs 2.5 MB). Helioviewer getClosestImage for the needed channels every 5 min, downloading an image only when its id changes (images are immutable per id, Cache-Control 30 d). GONG QR bqs every 60 min from the current day directory. SILSO once a day with If-None-Match (304 most days; file changes monthly). Back off on failure to at least 1 min (NWS guidance), then exponentially.
- Serve stale on error with an explicit maximum staleness per source (e.g. SWPC 30 min, AIA 3 h, GONG 24 h, SILSO 45 d). Past that, mark the source unavailable instead of caching an all-failed snapshot as success.
- Stop keying realtime data by exact jd. Use live data only when |sim jd - now| is within a small window (suggest 1 day) and otherwise report forcing as synthetic. For historical dates, if supported, quantise jd to the source cadence (e.g. 15 min for AIA, 1 h for GONG) and update tests/test_solar_realtime_data_cache.py on purpose.
- Replace SWPC ingestion with json/rtsw/rtsw_wind_1m.json and rtsw_mag_1m.json. Parse newest-first, filter active==true, take the newest active row with non-null fields, map density->proton_density, speed->proton_speed, temperature->proton_temperature, and surface the source spacecraft and row age. Isolate the plasma and mag feeds so one can fail alone.
- Fix GONG discovery: list the day directory (bqs/YYYYMM/mrbqsYYMMDD/), pick the newest mrbqs*.fits.gz, and key the PFSS cache by that file name, not jd. Coordinate with the H-2 owner, because this switches PFSS from synthetic to observed input.
- Replace getTile(x=-1,y=-1,native scale) with a full-disk product (e.g. downloadImage?id=<id>&scale=8&type=png: 512x512, about 130 KB). Then either reproject the disk to lat/lon, or change the shader to project the Earth-facing hemisphere. Pass rsun/scale metadata to the coronal-hole detector instead of the 0.90 constant.
- Make the tile route serve by image_id from the in-memory image store (404 or 409 if unknown or expired) rather than 'whatever latest is now'. Add Access-Control-Expose-Headers if the frontend is ever to read the X-Solar-AIA-* headers.
- Enforce an overall wall-clock deadline per upstream fetch (httpx with connect, read and total limits, or an asyncio.wait_for around the whole fetch), because urllib's timeout is per socket operation.
- Add the preview origins (http://127.0.0.1:4173, http://localhost:4173) to SOLAR_CORS_ALLOWED_ORIGINS or make them configurable. Tile images are loaded with crossOrigin='anonymous' and need ACAO.
- Remove or authenticate force_refresh and force_data_refresh on public routes, and rate-limit /solar/realtime. The refresher alone should decide when upstream is contacted.
- Make source_status honest: GONG ok only when a FITS map was parsed, plus per-source age and error. Consider surfacing 'live data unavailable' in the UI.
- Emit ISO-8601 UTC ('...Z') image dates from the backend, and stop the frontend from Date.parse-ing zone-less strings.
- Add UI attribution: 'Courtesy of NASA/SDO and the AIA, EVE, and HMI science teams', 'Source: WDC-SILSO, Royal Observatory of Belgium, Brussels', NOAA SWPC, the Helioviewer Project, and the NSO/GONG acknowledgement. Get a product decision on the SILSO CC BY-NC non-commercial clause.
- Add contract tests using recorded real payloads (keep the upstream_raw fixtures) plus a scheduled live canary that fails on 404s or schema drift. The SWPC break went unnoticed for about 5 months because every test stubs _fetch_snapshot.
- A background refresher removes only 1.8-3.1 s of I/O per physics call. The measured 7.8 s compute still exceeds the 2.6 s client timeout, so H-1 also needs compute caching or decoupling (other investigators' areas).

# AREA: config-deploy

## Summary
The web page finds the backend by guessing: it takes whatever hostname the page was opened on and always adds port 8042. Nothing (no setting, no environment variable, no URL option) can change that, and no Vite config file exists anywhere in the repo. The backend only accepts browser requests from a short hard-coded list of page addresses (ports 3000 and 5173). So only `npm run dev`, `dev:ui` and `dev:full` opened at the address the terminal prints actually work. `npm run preview`, a dev server that fell back to the next port because 5173 was busy, opening dev:full from another machine's IP, or a production build hosted elsewhere are all rejected by the browser. A rejected request still does its full job on the server: it uses a compute slot and a rate-limit token, and then the browser throws the answer away. It also hides the real error (for example 'server busy'), so the app cannot react to it or show it. I confirmed that a same-origin proxy (Vite's server.proxy, which the preview server inherits automatically in Vite 7) removes this whole class of failure in both dev and preview. With the proxy and a longer client timeout, the page got real physics data and loaded the live solar (AIA) image for the first time. A careless proxy setup breaks other things, though. A '/solar' rule swallows the static '/solar-systems' files. Returning an empty backend address silently turns off the solar image. Routing everyone through a proxy puts all users on one rate-limit bucket, and the default server settings let clients fake their identity. Fixing CORS alone will not make the sun work: requests still take 7-12 s against a 2.6 s client timeout, and the rate limit (36 per minute) is lower than the client's own polling rate once responses get fast. The backend is always started with auto-reload and one process, and there is no startup hook yet, so any background refresher is a new feature that has to plan for restarts and possible multiple processes.

## hidden_problems
- Making the origin 'allowed' does not by itself make the sun work. Once CORS passes, the client sees the real problem: 7-12 s responses against a 2.6 s client timeout, plus 12 s server-side compute-timeout 503s (R5, R6). Fixing CORS without fixing latency and timeout only swaps 'CORS error' for 'aborted' and '503'.
- Rejected origins still cost the server full compute, a concurrency slot and a rate-limit token (the backend returned 200 while the browser discarded it). The audit's '14x CORS-blocked' preview requests were real work that kept the 2 guard slots busy too.
- Cross-origin, a 503 or 429 is unreadable when the origin is rejected, and Retry-After is not exposed even when it is allowed (no expose_headers). Any 'honour Retry-After' or 'show error state' client fix fails silently cross-origin unless expose_headers is added. Unhandled 500s never carry ACAO, so they always look like CORS/network errors.
- If backendBaseUrl is changed to return '' (the obvious 'relative URL' fix), physics works but the AIA texture is silently never requested: buildAiaProxyTextureUrl returns null for an empty base (solarObservationTexture.ts:125-127).
- A proxy key of '/solar' also captures the static /solar-systems/manifests/*.json files (Vite uses startsWith), which then 404 from the backend. The latent nearby-systems/local-system feature would break when it is wired back in.
- Behind a same-host proxy every browser arrives as 127.0.0.1. All tabs and users share one 36/min rate-limit bucket and one pair of compute slots. uvicorn (proxy_headers=True by default, trusts 127.0.0.1) and _client_identity (first XFF hop) both honour a client-supplied X-Forwarded-For, which the Vite proxy passes through untouched, so identity becomes spoofable and the two layers disagree on who the client is.
- The rate limit (36 per 60 s) is lower than the client's steady-state polling (about 60/min at 900 ms once responses are fast). A successful latency fix would turn aborts into 429s within about 40 s for a single tab.
- SOLAR_CORS_ALLOWED_ORIGINS replaces the default list, so a user who adds :4173 for preview silently breaks :5173 dev, and the WebSocket allowlist inherits the change. A '*' entry is silently ignored instead of rejected.
- Port coupling is spread across several files. dev:full --backend-port is not forwarded to the frontend, which always calls 8042. dev:full --frontend-port, Vite's automatic port fallback (strictPort=false) and LAN-IP access all land on non-allowlisted origins. The four hard-coded 8042 copies will drift if only main.ts is fixed.
- --reload (used by every documented launch) restarts the worker on any .py change. That clears the realtime/tile caches and rate-limit state, and is currently the only thing that kills orphaned compute threads. --workers N (unused today, and mutually exclusive with --reload) would multiply the slots (2N), the rate-limit buckets and any background refresher's upstream traffic, with a cold cache per worker.
- There is no lifespan hook, and all 6 backend test modules use a module-level TestClient(app) without `with`. A refresher added via lifespan will not run in the existing tests, and code that assumes a warm cache will behave differently under test.
- VITE_BACKEND_URL-style settings are baked in at build time (import.meta.env is inlined as a literal object), so one static build cannot be re-pointed at deploy time without a rebuild or a runtime mechanism (a query param, or a fetched config.json).
- A static build hosted under a sub-path would also break the absolute asset URLs such as '/data/asteroid-phase1/...' (phase1AsteroidCatalog.ts:149-150; no Vite `base` is configured). This is not H-1, but a 'serve the build elsewhere' fix will hit it.
- Client aborts produce no line in the uvicorn access log, so server logs undercount failures. Monitoring an H-1 fix from the backend logs alone will look better than reality.
- In the browser tests, a page whose document was produced by Playwright route.fulfill could not reach the loopback backend at all (it failed in 3 ms and never reached the server). This is likely Chrome's local-network-access rule treating that document as public. The same rule could block a publicly hosted page from calling a localhost backend.
## fix_implications
- Default to same-origin. Add a vite.config.ts (none exists) with server.proxy; preview inherits it automatically in Vite 7. Either use an explicit anchored matcher (e.g. regex '^/(solar|trajectory|mission|nearby-systems|health|info|bodies|benchmark)(/|\\?|$)', or at least '/solar/' with the trailing slash), or move the API under an '/api' prefix with rewrite. Never use the bare '/solar' key. Add ws:true for /ws/sim when the WebSocket client is wired in.
- Point the proxy target at an explicit IPv4 loopback plus an env-driven port (e.g. process.env.BACKEND_PORT ?? 8042 → 'http://127.0.0.1:${port}'), not 'localhost', which can resolve to ::1 on other hosts while uvicorn binds IPv4. dev:full must pass --backend-port to Vite through that env var.
- backendBaseUrl should resolve in this order: runtime override (?backend=, restricted to http(s) and preferably same-site or dev-only), then build-time VITE_BACKEND_URL, then window.location.origin. Never return '' (it breaks the AIA URL builder), or else make buildAiaProxyTextureUrl accept a relative base. Put it in one shared module (next to createRuntimeUiConfig in src/frontend/app/sceneSetup.ts, or a new runtimeConfig.ts with a readRuntimeString sibling of readRuntimeNumber) and import it from main.ts and trajectory/index.ts to remove the duplicate 8042 copies.
- Expose the solar client options through createSunController's options, using the readRuntimeNumber idiom (param, then VITE_ env, then fallback, with clamps): e.g. ?solarTimeoutMs / VITE_SOLAR_TIMEOUT_MS, ?solarPollMs / VITE_SOLAR_POLL_MS, ?solarForcing, ?solarLiveData, ?solarMaxFeatures. Remove the hard-coded block at sunController.ts:152-160. Keep the SolarPhysicsClient clamps (timeout ≤ 20 s).
- Client timeout and server compute budget must be designed together. The client timeout needs to exceed SOLAR_PHYSICS_COMPUTE_TIMEOUT_SECONDS (12 s) plus the proxy hop, or the server must really cancel abandoned work. Otherwise every abort creates an orphan that holds one of the 2 slots.
- Reconcile the rate limit with the poll cadence. Either lower the steady-state poll rate (e.g. only re-poll when the sim date changes meaningfully) or raise or rescope SOLAR_PHYSICS_RATE_LIMIT_PER_WINDOW. Account for the fact that a proxy funnels all users into one identity.
- Keep a backend-side safety net for users running without the proxy: add http://localhost:4173 and http://127.0.0.1:4173 to the default list (or use allow_origin_regex for loopback on any port in dev), and add expose_headers=['Retry-After'] (plus the X-Solar-AIA-* headers if they are ever read). Consider allow_credentials=False, since the frontend never sends credentials. Document, or make additive, the replace semantics of SOLAR_CORS_ALLOWED_ORIGINS (e.g. an extra SOLAR_CORS_EXTRA_ORIGINS), and reject '*' loudly rather than silently.
- Coordinate with the X-Forwarded-For finding. With any same-host proxy, set uvicorn --forwarded-allow-ips deliberately (or proxy_headers=False) and make _client_identity use request.client.host, or the proxy's appended last hop, instead of the first XFF hop. The Vite proxy should not pass client XFF through untouched when the result is trusted.
- A background refresher belongs in a FastAPI lifespan= handler added at server.py:84 (on_event is deprecated). It must survive --reload restarts (cold start on every .py edit), assume one worker or use an external cache, stay off (or be stubbed) in tests that use the module-level TestClient, and respect the existing singleflight/cache TTL in SolarRealtimeDataProvider.
- Production needs an explicit recipe, since Vite preview is not a production server. Either a reverse proxy mapping the same path prefix to the backend (same-origin, so no CORS), or split hosting with VITE_BACKEND_URL at build time plus SOLAR_CORS_ALLOWED_ORIGINS on the backend. Also update the README: it has no CORS guidance, a stale 'Connect' step, and recommends `npm run preview`, which is rejected today.
- Add tests that currently don't exist: a unit test for the backendBaseUrl/runtime-config resolution order (sceneSetup.ts has no test file), a test that the AIA URL is non-null for the chosen base, and a backend test asserting ACAO and exposed Retry-After for each supported dev/preview origin.
## open_questions
- Should a runtime ?backend= override be allowed in production builds? It lets a crafted link feed the app attacker-controlled physics data and textures. Alternatives: dev-only, or same-origin/allowlisted hosts only.
- Is there any intended production deployment? No Docker, Procfile, CI or hosting config exists, so it is undecided whether the product owner expects same-origin reverse-proxy hosting or split static+API hosting.
- Should backend routes move under an '/api' prefix? That cleanly separates them from static paths like /solar-systems, but changes README curl examples and backend tests. The alternative is an enumerated proxy regex over the current root paths.
- Will the backend ever run with --workers > 1? That decides whether caches and a background refresher can stay in-process.
- Chrome's local-network rules for a publicly hosted page calling a loopback or LAN backend were not verified with a real public origin. The block I saw came from a Playwright route-fulfilled document, which is a test artifact.
- All physics latencies measured here (7.5-12.4 s) were taken while other investigators' software-GL browsers held the host at load average 53 on 32 cores. Use them only as evidence that the requests got through, not as performance numbers.

# AREA: frontend-consumers

## Summary
Today the Sun users see is entirely the offline stand-in: no server solar data ever reaches the screen, and nothing tells them so. The header even keeps saying "Live simulation". What users lose today: (1) about 144 coronal loops and eruption arcs around the Sun (today there are none), (2) the solar-wind spiral lines in the zoomed-out view (none), (3) magnetic field lines computed from data (today a simple symmetric bar-magnet pattern), (4) up to 8 sunspot groups placed from data (today one fake spot), (5) mapped coronal holes (today a generic pattern over the poles), (6) any real SDO/AIA image (it is never even requested), and (7) any solar activity level. A separate bug makes the fallback render activity 0, a completely quiet Sun, instead of the intended solar-cycle model (0.75 for today's date). Flares and CMEs never show at the default scale, with or without data, because they are deleted on their first frame. The observation-channel dropdown still recolours the procedural Sun, but it cannot load an image until data arrives. Making the server faster is not enough on its own. At the default speed the simulation moves 4 days per second, so the app asks for a new date every 0.9 s. Each new date defeats the server's caches (about 5 s to compute a new date, 0.02 s for a repeated one), and the request rate would pass the server's limit of 36 per minute. Once data does flow, several display paths that have never run switch on at once. Solar-wind lines are drawn about 80 times too large (out to about 240 AU, past Neptune). Loops reach beyond Mars' orbit. Sunspots and flare origins land near the poles because the server and the browser disagree on which axis is north. The corona switches to a 193 Å false-colour tint by default. The field lines drawn with the H-2 maths error become visible. The browser itself handles the data easily: about 2-4 ms to parse a 655 KB response and about 1 ms per frame to animate it. So the fix needs slower polling that knows which date is being shown, an honest status indicator, and these display fixes, shipped together or behind a flag.

## hidden_problems
- The 'model' fallback is broken as well: the Number(null)===0 bug pins activity at 0. If H-1 is fixed and data later drops out, or if a fix relies on the fallback, users still see a flat, quiet Sun. Fix sunController.ts:405-410 together with H-1.
- A faster backend alone trips the rate limit. The success cadence of max(0.9 s, latency) plus one frame (up to about 66/min per tab) exceeds the 36/min per-IP limit, so the app would flip between data and 429s every ~30 s. The client ignores Retry-After and treats 429 like any error.
- Any running sim sends a new jd every poll, down to 0.86 ms resolution, so the PFSS and realtime snapshot caches (keyed on the exact jd) miss every time: 5 s of CPU per request. Only a paused sim hits the cache. At 4 d/s even a 1-day jd bucket changes 4 times per second of wall time, so caching alone cannot rescue per-epoch recompute.
- The first data to arrive switches on display paths that have never run: the Parker spiral out to 242 AU and loops out to 1.8 AU at the default scale, poles 90 deg off (z-up vs y-up), 54% of sunspots and flare origins above 40 deg, loops and PFSS in different frames, likely double rotation, and H-2's wrong PFSS lines. Enabling data without these fixes makes the Sun look visibly wrong.
- In Auto mode, data arrival silently changes the default Sun to the 193 Å false-colour tint (corona channelMode 3, loops recoloured). observationBlend also jumps from 0.013 to 0.85, overlaying a quarter-disk AIA tile wrapped as a globe texture. Product owners may read this as a regression.
- Flares/CMEs stay invisible at the default scale even with data, because the lifetime is negative when the display radius (0.3755 AU) exceeds cmeMaxDistanceAu (0.3). 'Flares from data' gains nothing unless solarFlares.ts:225-228 is fixed.
- The client clamps pollIntervalMs to at most 30 s and timeoutMs to at most 20 s (solarPhysicsClient.ts:58-59). Setting poll=60-120 s or timeout=30 s silently turns into 30 s and 20 s.
- Raising the timeout to 20-30 s makes requests back-to-back, because the next one is scheduled from the start time. One tab would then hold a server slot nearly all the time, and two tabs would saturate the 2-slot guard. A response that arrives 20-30 s later is also 80-120 sim days stale, but it is applied as current: there is no epoch check.
- A 'refresh now' after 'Jump to now' cannot pre-empt a slow in-flight request, because the inFlight check precedes the force check (sunController.ts:498-499). If the client's force path is ever used, its finally block clobbers inFlight and abortController for the newer request (solarPhysicsClient.ts:156-162).
- The frontend always sends live_data=true and forcing=hybrid. The backend blends today's SWPC/SILSO data into any epoch with wall-clock confidence, and the AIA proxy always serves the 'latest' image regardless of epoch. Once data flows, 2031 or 1995 will quietly carry today's observations.
- After one success, the state is never cleared, so later failures stay invisible: the last payload stays on screen indefinitely, even years of sim time away. A status label driven only by 'last request failed' would therefore contradict what is drawn.
- The magnetic-field group is rebuilt on nearly every success (the signature includes feature brightness), even with the toggle off. Destroying and recreating 120 geometries and materials per poll adds GPU churn.
- Each poll carries 655 KB uncompressed with no GZip middleware, and 11% of it is fields the frontend never reads. A fixed high-frequency poll costs about 43 MB/min per tab.
- The Playwright CORS check of the AIA tile is inconclusive: Playwright's route.fulfill adds Access-Control-Allow-Origin automatically. Tile CORS on 4173 and other origins must be verified against a real server.
## fix_implications
- Decouple data cadence from the frame loop. Poll at 30-120 s, or only when a quantized epoch key changes. Raise or remove the client clamps (solarPhysicsClient.ts:58-59). Add exponential backoff with jitter, honour Retry-After and 429, and pause polling when document.hidden.
- Quantize the requested epoch (for example to 6 h or 1 d, or to the Carrington rotation) on the client, and key the server caches on the same bucket. While the sim runs fast, prefer one request per bucket, and animate rotation client-side from the last payload.
- Make the mode depend on the epoch. Use live_data=true and forcing=hybrid only when |simJd - nowJd| is under about 1 d (or when paused after 'Jump to now'); otherwise use forcing=synthetic and live_data=false, and suppress the AIA texture. Pass jd to the aia-tile proxy or stop pretending image_id selects the image.
- Check response epochs: drop or down-weight payloads whose epoch_jd is far from the current simJd, and expire or clear solarPhysicsState on large jd jumps or after N minutes, so the fallback returns rather than frozen data.
- Fix the activity fallback (Number(null) -> 0) in sunController.ts:405-410 so the 'model' state shows the Hathaway cycle. This is a prerequisite for an honest 'Solar data: model' label.
- Before or with enabling data, ship the display fixes: scale data geometry by physical radius or clamp its extent at non-realistic scale (Parker 242 AU, loops 1.8 AU); convert backend z-up to frontend y-up at ingest; attach loops and PFSS to the same frame and remove the double rotation; gate PFSS on the H-2 fix; fix the flare lifetime at display scale.
- Add a solar status indicator (#status-solar in #status-bar) using the #status-catalog pattern: role=status, aria-live, data-solar-state live/model/unavailable/stale, and a renderer like catalogSourceStatus. Expose a getSolarDataStatus() from sunController built on client.status() plus the epoch mode. Make the static 'Live simulation' badge truthful.
- Reorder the sunController guards so force can pre-empt, or cancel explicitly on 'Jump to now'. In the client, clear inFlight and abortController only when currentReqId === _reqId.
- Decouple the blend duration from pollIntervalMs (a fixed 1-2 s). Blend the first arrival too, and blend the raw-state layers (activity, observationBlend, sunspots, holes) so rare updates don't pop.
- Decide the Auto-channel default explicitly: keep the white-light look unless the user picks a channel, or accept the 193 Å tint as the new default. Treat the AIA tile as a disk overlay or billboard, not a globe texture.
- Shrink the payload: add GZipMiddleware, round arcs to about 4 decimals, drop unread feature fields (74 KB), and make the magnetic-field signature ignore brightness jitter so field lines rebuild only when the PFSS source or rotation changes.
- Include the CORS allow-list for every served origin, preview 4173 included, for both /solar/physics and /solar/realtime/aia-tile, because the TextureLoader uses crossOrigin='anonymous'.

# AREA: tests-contracts

## Summary
The current tests all pass, but none of them would catch the failure behind H-1. The frontend has no tests at all for the code that fetches sun data, drives the sun visuals or picks the solar image. The backend tests call the sun endpoint in a cheap mode (no live data), not the mode the app uses, and they never check how long a request takes, whether the browser's origin is allowed (CORS), or what happens when two requests pile up. The backend and frontend do not share a data contract. The backend returns an untyped dictionary, and the frontend has four hand-written partial copies of the shape that already conflict with each other. There is no CI of any kind, so nothing runs these tests automatically. I wrote 29 draft tests (10 frontend, 18 backend plus one timing test, plus a browser acceptance script) and ran them against the current code. They fail where H-1 says they should: 8 of 10 frontend drafts, 12 of 17 backend drafts, the timing test, and the browser acceptance (0 of 28 successful sun-data requests on the dev address, 0 of 14 on the preview address, no solar images loaded). A control run where I made the backend cheaper did show successes and one solar image loading, so the harness can detect a working fix. Two traps matter for planning. First, making the server fast is not enough: the app then asks about 66 times a minute, the server allows 36, and the failure just changes from timeouts to rate-limit errors. Second, at the default simulation speed (4 days per second) the requested date moves about 3.6 days between polls, so caching by date alone will rarely hit. The fix has to make a first-time request fast, or serve the last good answer while it recomputes.

## hidden_problems
- Rate limit after the fix: once the server answers quickly, the client polls about 66 times a minute (poll measured from request start, 900 ms) against a server limit of 36 per 60 s per client (server.py:168-177). A server-only fix turns timeouts into 429 bursts plus 6 s backoffs and fails the 95% acceptance. Several tabs on one IP share the limit.
- Default sim speed of 4 d/s (src/constants.ts:12) moves jd about 3.6 days per poll. A cache keyed on jd buckets, even day-sized ones, rarely hits in default play. existing test_pfss_cache (tests/test_pfss_cache.py:33-57) deliberately treats jd one day apart as distinct keys, so coarser quantisation breaks that test. The first request for a new date has to be fast in its own right, or the server has to return the last good answer while it recomputes (stale-while-revalidate).
- The PFSS cache key includes the blended activity float, which drifts with datetime.now() in live mode, so even identical requests miss. A quantisation-only fix, tested with a snapshot that has no timestamps, looks green in tests and still misses in production.
- tests/test_compute_budget.py:47-49 asserts that a timed-out worker keeps its guard permit. Releasing the permit on abort or timeout breaks it. The compatible designs are single-flight joining of identical in-flight work, or cooperative cancellation, which also needs an owner_cancel_event passed at server.py:1050-1061 and checked inside the PFSS loops.
- Offline tests that simulate upstreams by refusing DNS pass at HEAD (fast degraded 200). Real outages often hang instead, giving 4 sequential waits of about 15 s, so a 503 at 12 s and a held permit. The 'upstream offline' test must simulate hangs, or it gives false confidence.
- gong_synoptic.ok is always true (sim/solar_realtime_data.py:809-823). A provenance flag built from source_status will say GONG is live when it is not; the real GONG outcome is only visible as pfss_field_lines.source.
- The backoff is duplicated: sunController.ts:531 re-imposes its own 6 s / pollInterval gate on top of the client's nextRefreshMs. Exponential backoff or Retry-After support in the client is overridden unless this second gate is removed.
- Test isolation: rate-limit deques, the concurrency guard and the snapshot/PFSS caches are module globals. New API tests push the file toward the 36/60 s limit (validation calls count too, since rate limiting runs before validation, server.py:1001-1002), and an orphaned test job can hold a real guard permit into the next test. Every new test needs fresh-state fixtures.
- Making requests succeed adds about 0.55-0.6 MB of JSON per poll (roughly 36 MB/min at 0.9 s cadence) plus main-thread JSON.parse. A payload-size budget belongs in the contract before the fix ships.
- Once PFSS results reach the client, the H-2 wrong-Legendre field lines start rendering. No existing test covers dipole purity or Legendre values (tests/test_solar_physics_model.py:186-236 only check open/closed counts and bounds).
- Allowlist CORS is fragile beyond :4173. dev-full binds both servers to 0.0.0.0 (scripts/dev-full.mjs:55), so LAN-IP origins are blocked. Without a vite config (none in the repo), Vite moves to 5174+ when 5173 is busy, which silently loses the backend. Adding origins to the list also widens WebSocket origins (server.py:150-153).
- The Playwright harness has its own trap: serving the page by interception makes Chromium's Local Network Access check block localhost calls (19/19 'LocalNetworkAccessPermissionDenied'). The flag --disable-features=LocalNetworkAccessChecks is needed; a real dev server does not hit this.
- Hermetic CI cannot meet the '>=1 AIA tile' criterion without an upstream fixture: with upstreams blocked, sdo_aia is null and no tile is ever requested. The e2e job needs a snapshot/tile shim or a fake Helioviewer.
- The frontend payload interfaces already conflict (tsc: heliosphere unknown vs structured), and 246 unrelated strict errors mean a typed contract only gets enforced if typecheck runs on a scoped include or the errors are fixed first.

# AREA: backend-profile

## Summary
I measured the default request the frontend sends, and it can't meet the frontend's 2.6-second deadline, even on a fast machine. Each request takes about 8 to 10 seconds when the server is otherwise idle. About two thirds of that is one piece of maths: tracing the magnetic field lines (the "PFSS" step, which audit finding H-2 separately reports as wrong). The other third is waiting on about 10-13 downloads from outside services, fetched one after another. Building the corona features and turning the answer into JSON take only a few hundredths of a second. The caches don't help. They only reuse a result when the date is exactly the same, and the frontend sends a new date on every poll. The live-data blend also shifts a little with the wall clock, so even two identical requests a few seconds apart recompute the field lines. The server allows two jobs at once, but in Python that makes things worse: two jobs together took 21-24 s each, compared with 7 s for one alone. In the real-server test, both admitted requests hit the server's 12 s time limit and failed, and the other two were turned away at once. When the browser gives up on a request, the server keeps working on it: the slots stayed busy about 22 s after the client left. When the outside services are down, the page still gets a usable fallback answer after about 5 s. When those services are slow instead of down, a request takes 21-46 s, and the response doesn't clearly say it has fallen back. The main output for cache design: the costly field lines only really change every 14.4 minutes of simulated time, and the cheap features change every minute. So the fix is to take downloads off the request path, cache the field lines per 14.4-minute block with an activity value that doesn't drift, and recompute the cheap parts on every request. The host was busy with other investigators' browsers during my runs (load average 17-25 on 32 cores), so treat the absolute timings as a bit pessimistic. The proportions and pass/fail results hold.

## hidden_problems
- A cache keyed on jd alone won't hit. PFSSCache keys on the exact activity float, and hybrid/live activity drifts with the wall clock (freshness weights, solar_physics.py:394). Even identical requests 30 s apart miss and recompute PFSS for 6-7 s.
- The realtime snapshot cache keys on the exact jd float (solar_realtime_data.py:131). The data is really wall-clock-driven: SILSO is daily, SWPC is 'latest', and AIA returns the newest image for any future jd. A jd-keyed snapshot cache refetches 3-4 MB per poll and gains nothing.
- The float bucket boundary is fragile: int(jd*100) puts 2461308.55 into bucket ...854. A server-side bucket key must use exactly the same arithmetic as the RNG seed, or it will serve a field line set from the neighbouring bucket.
- Time-warp breaks any 14.4-minute bucket cache. At 1 sim-day per wall-second, every poll lands in a new PFSS bucket and needs 5-7 s of compute. A fix needs a policy for time-warp: lower fidelity, skip PFSS, or precompute ahead.
- Raising SOLAR_PHYSICS_CONCURRENT_REQUEST_LIMIT or HEAVY_COMPUTE_THREAD_LIMIT makes things worse. The PFSS tracer is GIL-bound Python, and two concurrent jobs take about 3x longer each, which pushes both past the 12 s server timeout.
- The server timeout (12 s) doesn't cancel work, and a job that finishes after timing out caches its result under a key no later request will use. The work is wasted and both slots stay busy about 22-29 s. The shared 2-worker executor probably also starves trajectory and mission endpoints.
- Making the request faster doesn't remove the upstream-hang risk. With slow upstreams, one request takes 21-46 s, because each source adds its own timeout one after another, and the GONG listing fetch (3.5 s timeout) sits inside the PFSS compute even when live_data=false.
- A degraded snapshot is cached as a success for 120 s. If an outage cache is built on the current code, fallback results will be served for the TTL after upstream recovers, with only buried flags to show it.
- Response status flags mislead: gong_synoptic.ok is always true (no I/O is done), live_data_enabled just echoes the request, and pfss source is always 'synthetic'. A UI 'live data' badge built on these fields would be wrong.
- Live and offline states differ a lot (activity 0.55 vs 0.76). Intermittent upstream failures will make the rendered corona jump between two different feature and topology sets.
- The NOAA SWPC feeds return 404, so the most heavily weighted live source (0.45) is dead. The GONG regex never matches (the listing contains only sub-directories). If someone fixes GONG ingestion, a per-rotation FITS download of several MB joins the request path.
- The rate limiter counts 503s. A client that retries quickly on 503 (for example honouring Retry-After: 2 across two tabs) will hit 429 at 36/min.
- Fixing H-1 as things stand starts shipping PFSS lines, which audit finding H-2 reports as wrong. They are also 98% of the cost and 21% of the payload, and 3-25 of 120 lines jump between neighbouring polls even inside one bucket, because footpoint importance sampling reacts sharply to tiny activity changes. Users would see flicker.
- The 640 KB responses are sent uncompressed at up to 1 poll per 0.9 s. Encoding takes 25-40 ms on the event loop, which adds latency to /health and every other request.
## fix_implications
- Take upstream I/O off the request path. Refresh the realtime snapshot in the background on a wall-clock TTL (for example 2-10 min; AIA cadence and SILSO's daily rows justify it), fetch the 5 AIA channels in parallel or on demand, and have requests read only the last good snapshot. Key it on wall-clock time, or at most on a coarse jd bucket for historical epochs.
- Cache PFSS on (floor(jd*100) exactly as the seed computes it, fidelity lines/lmax, a quantised or frozen activity), for example activity rounded to 0.01 or taken from the synthetic cycle only. Use single-flight per key so concurrent polls share one computation. At 1x speed that is one 5-7 s computation per 14.4 min of sim time per fidelity level.
- Recompute features, parker spiral and assimilation scalars per request (together under about 50 ms). They are the fast-varying part (identity churn about 1% per sim-minute), so caching them isn't needed and would make the animation step visibly.
- Keep a single compute worker, or move PFSS to a process pool. Don't raise the thread limits. Consider splitting the endpoint (fast state vs slow field lines) so the frontend's 2.6 s deadline applies only to the fast part.
- Precompute the next PFSS bucket ahead of time, or give time-warp an explicit degrade path (drop field lines or lower fidelity when jd moves more than 0.01 d per poll).
- Make cancellation real (a cooperative cancel event checked in the RK4 loop), or make sure a finished job's result lands in a cache that later requests will use.
- Add a top-level degraded/live_data_used flag with per-source age. Make gong_synoptic report truthfully, or remove it. Don't cache all-failed snapshots for the full TTL.
- Add gzip (level 1 is enough: 57% smaller in 4 ms) and round floats to 4 decimals (636 KB to 121 KB gzip). Consider moving JSON encoding off the event loop (return a pre-encoded Response from the worker).
- Settle H-2 first, or ship with field lines off by default. Field lines are 98% of compute, 21% of payload, and currently wrong.
- Check any latency acceptance target on an idle host, and on the frontend's real sequence of jds, not repeated identical jds. Identical jds hit caches that production traffic never hits.
## open_questions
- Is the wholesale field-line change every 0.01 d (the RNG seed int(jd*100)) wanted, or an artefact? The answer decides whether the PFSS cache bucket is 14.4 min of sim time or something coarser.
- What should the server return while a new PFSS bucket is computing (the previous bucket? no field lines?), and how should time-warp above about 1 bucket per poll behave?
- Absolute timings on an idle host: my runs had loadavg 17-25 from other agents. The audit's idle-host figure was 4.6-9.4 s; my sequential real-server run gave 8.2-10.3 s.
- Would the project accept a process pool (or free-threaded Python) for PFSS, or should the tracer be vectorised? Vectorising would remove about 5 s of pure-Python per-point evaluation.
- Should live forcing keep blending by wall-clock freshness? That blend makes responses non-reproducible for identical inputs and defeats any cache keyed on activity.
- Not measured: the cost of a working GONG FITS ingestion, and the effect of the H-2 Legendre fix on PFSS runtime.
