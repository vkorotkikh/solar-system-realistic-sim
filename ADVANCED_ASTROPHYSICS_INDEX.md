## 9. Proposed Organizational Structures

### Option A: "Physics Domain" Organization (recommended)

Group everything by physics domain. Consolidates the 16 SMBH shockwave variants into a canonical set.

```
research/
├── smbh-shockwaves/
│   ├── CANONICAL_RESEARCH.md          (merge of best content from 16 variants)
│   ├── hypotheses/
│   │   ├── H01-H05_core.md
│   │   ├── H07-H16_radical.md
│   │   ├── H17-H26_quantum_gravity.md
│   │   ├── H27-H30_extreme.md
│   │   └── HYPOTHESIS_REGISTRY.md
│   ├── papers/
│   │   ├── bibliography.bib
│   │   └── paper_catalog.md
│   └── implementation/
│       ├── architecture_plan.md
│       └── h29_warp_wave_plan.md
├── superluminal/
│   ├── analysis.md
│   ├── math_approaches.md
│   ├── implementation_notes.md
│   └── latex/
│       ├── unified_thesis.tex
│       └── (other .tex files)
├── solar-physics/
│   ├── overhaul_plan.md
│   ├── overhaul_report.md
│   ├── corona_gaps_plan.md
│   └── sun_model_analysis.md
├── cosmology/
│   ├── hierarchical_architecture.md
│   └── nearby_star_systems.md
└── reference/
    └── physics_catalog.md
```

**Pros:** Clean separation by physics domain. Easy to find things. Natural hierarchy.
**Cons:** Requires moving/consolidating many files. Breaks git history for moved files.

### Option B: "Document Type" Organization

Group by what the document IS rather than what physics it covers.

```
research/
├── hypotheses/          (all H1-H30+ docs)
├── literature-reviews/  (paper catalogs, bibliographies)
├── implementation-plans/ (all architecture/plan docs)
├── analysis/            (deep analysis, math approaches)
├── latex/               (all .tex and .bib)
└── reference/           (physics catalog, nearby systems)
```

**Pros:** Simple mental model. Clear what you're looking for by document type.
**Cons:** A single hypothesis spans SMBH, QG, and superluminal -- the physics context is lost.

### Option C: "Maturity Stage" Organization

Group by how far along the idea is: pure research vs. planned vs. implemented.

```
research/
├── 0-ideas/             (radical, speculative, not yet planned)
├── 1-researched/        (literature reviewed, hypotheses formulated)
├── 2-planned/           (architecture designed, implementation plan written)
├── 3-implemented/       (code exists and runs)
├── 4-validated/         (tested and verified)
└── archive/             (superseded variants, old drafts)
```

**Pros:** Instantly see what's actionable vs. what's theoretical. Natural workflow pipeline.
**Cons:** Files move between stages, requiring maintenance. Some files span stages.

### Option D: "Minimal Cleanup" -- Index Only (what we're doing now)

Keep files where they are. Create this index as the single source of truth for navigation. Add a `research/archive/` for the 10+ duplicate/variant SMBH shockwave files.

```
(current structure, unchanged)
├── ADVANCED_ASTROPHYSICS_INDEX.md    (THIS FILE -- master navigation)
├── my-notes/                          (keep as-is)
├── superluminal_*.md                  (keep in root)
├── h29-*.md                           (keep in root)
└── research/
    └── archive/                       (move duplicate variants here)
```

**Pros:** Zero disruption. No broken git history. This index serves as the map.
**Cons:** Files remain scattered. Root directory stays cluttered with 16+ superluminal files.

## 10. Recommendation

**Option A (Physics Domain)** is the cleanest long-term structure, but it's a significant reorganization.

**Option D (Minimal + Index)** is the pragmatic choice for now -- this file already serves as the map, and the only immediate cleanup needed is archiving the 10+ SMBH shockwave variant files that are superseded by the MASTER versions.

A hybrid approach: do Option D now, then migrate to Option A incrementally when the Phase 1 implementation begins and the `research/` directory would be created naturally alongside the new code modules.
