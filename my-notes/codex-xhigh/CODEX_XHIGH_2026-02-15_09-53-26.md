# Post-Phase-1.1 Strategic Roadmap (As of 2026-02-15)

## 1. Current Position
- Phase 1 foundation is now in place: ranked nearby-system catalog, backend endpoint, and frontend marker/label rendering.
- Phase 1.1 (searchable explorer + marker-point picking) is the right immediate UX completion step.
- The biggest long-term challenge is not rendering markers, it is multi-scale correctness: AU-scale local simulation and light-year-scale interstellar navigation in one coherent frame.

## 2. North-Star End State
- Seamless zoom from Solar System to nearby stars with physically consistent positions over time.
- Click any nearby system and transition into a local high-fidelity simulation scene.
- Fidelity-tiered systems:
  - Tier A: high-confidence, data-rich systems with robust dynamics.
  - Tier B: medium-confidence approximations.
  - Tier C: marker-only systems.
- Scientific provenance visible in-app for each system and body.

## 3. Key Decisions To Lock Early
- Canonical frame: backend stores all interstellar positions in ICRS/barycentric with epoch metadata.
- Unit policy: backend float64 in AU; renderer camera-relative float32 projection.
- Catalog contract versioning: `/nearby-systems` response schema should be versioned now.
- Fidelity model: every system manifest must carry tier + confidence + source references.
- Transition model: explicit mode state machine (`solar`, `interstellar`, `system_local`) to avoid hidden branching in UI/render code.

## 4. Post-1.1 Phases

### Phase 1.2: Hardening and Contract Discipline
- Add API schema version + validation tests for `/nearby-systems`.
- Add endpoint for single-system lookup (`/nearby-systems/{id}`) with aliases and metadata.
- Add fallback behavior for offline backend and explicit UI status.
- Exit criteria: deterministic payloads, contract tests, no render regressions.

### Phase 2.0: Multi-Scale Coordinate Engine
- Introduce floating-origin/camera-relative world transform layer.
- Maintain absolute positions in float64 and derive render-local coordinates each frame.
- Add origin rebasing thresholds to avoid precision artifacts.
- Exit criteria: stable picking/labels at >10 ly distances, no jitter in local zoom.

### Phase 2.1: Time-Accurate Astrometry
- Move proper-motion propagation to backend authoritative service.
- Prefer robust propagation model (Astropy space motion) for epoch handling.
- Include radial velocity and uncertainty placeholders in response metadata.
- Exit criteria: reproducible propagated coordinates across JD ranges.

### Phase 3.0: System Manifest Pipeline
- Define manifest schema under `solar-systems/` for each target system.
- Include stars, companions, planets, orbital params, confidence, and source links.
- Build ingestion scripts for curated top systems first.
- Exit criteria: at least 10 nearby systems with validated manifests.

### Phase 4.0: Zoom-In Handoff Architecture
- Implement transition from interstellar marker to local system scene anchor.
- Add async scene loading pipeline and progress states.
- Keep continuity: camera path, target lock, and time-state preservation.
- Exit criteria: selecting a nearby system reliably lands in local system view.

### Phase 5.0: Local-System Dynamics
- Tier A systems: true multi-body dynamics where data quality supports it.
- Tier B systems: approximated Keplerian or reduced-order dynamics.
- Tier C systems: contextual static/kinematic representation only.
- Exit criteria: at least 3 Tier A systems with stable, testable dynamics.

### Phase 6.0: Scientific QA and Trust Layer
- Build validation harness comparing propagated positions against reference datasets.
- Add uncertainty display and “data confidence” indicators in UI.
- Add provenance panel per system/body.
- Exit criteria: traceable source chain and reproducibility checks in CI.

## 5. Risk Forecast
- Precision risk (high): mixed AU/ly scales will cause jitter if float64 pipeline is not enforced.
- Data completeness risk (high): many nearby systems lack enough parameters for “Solar-System-like” fidelity.
- Scope risk (high): trying to make every nearby system high fidelity too early will stall progress.
- UX risk (medium): users may confuse marker visibility with loaded local-system simulation state.
- Performance risk (medium): labels/picking for large catalogs can degrade frame time.

## 6. Mitigation Strategy
- Hard cap near-term supported high-fidelity systems to a curated shortlist.
- Enforce fidelity tiers in code and UI, not just docs.
- Add telemetry for frame time, load time, and marker counts.
- Separate “catalog truth” from “simulation truth” through explicit manifests and contracts.

## 7. Suggested 90-Day Execution Plan
- Weeks 1-2: finish Phase 1.1 + 1.2 contract hardening and explorer UX.
- Weeks 3-6: implement multi-scale coordinate engine (Phase 2.0) and astrometry service (Phase 2.1).
- Weeks 7-10: manifest schema + ingestion for top 10 systems (Phase 3.0).
- Weeks 11-13: first zoom-in handoff and local system bootstrap (Phase 4.0).

## 8. Success Metrics
- Technical: no visible jitter during interstellar navigation at 60 FPS target.
- Scientific: coordinate propagation agrees with reference within defined angular/position tolerances.
- Product: user can discover, select, and transition into at least 3 nearby systems reliably.
- Operability: schema/version changes are tested and backward compatible.
